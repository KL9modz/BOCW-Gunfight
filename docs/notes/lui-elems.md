# LUI elements — positioned text from script, the route above the hint panel (2026-09-13)

**Read from the dump and the retail builtin table; the one-element probe (`src/gunfight_menu_c/`) RAN
2026-09-13: the element renders in MP — and a plain string in it is a fatal LUI error (below).** This note corrects the "ceiling" line in [hint-panel](hint-panel.md) and the "server script
cannot *create* HUD elements" line in [lui-events](lui-events.md): T9 has no *hudelem* builtins, but it has
their replacement — the **luielem** system — and it is scriptable from both VMs this project can inject into.

## What it is

`scripts/core_common/lui_shared.{gsc,csc}` defines `class cluielem`; `scripts/autogenerated/luielems/` holds
the concrete elements. The two general-purpose ones:

| element | fields (name, bits, type) | what it is |
|---|---|---|
| `LUIelemText` (`luielemtext.gsc:81-93`) | `x` 7 int · `y` 6 int · `height` 2 int · `fadeOverTime` 5 int · `alpha` `red` `green` `blue` 4 float · `text` string · `horizontal_alignment` 2 int | **one positioned text line**, own colour and alpha |
| `LUIelemImage` (`luielemimage.gsc`) | `x` 7 · `y` 6 · `width` 6 · `height` 6 · `fadeOverTime` 5 · `alpha` `red` `green` `blue` 4 float · `material` material | a positioned rectangle — a background box or a highlight bar, **if** a plain material name is accepted (no stock caller ever sets one) |

Server-side pixel helpers divide by 15 (`luielemtext.gsc:186-198`: `set_x( int( px / 15 ) )`), so `x` spans
0–1905 px and `y` 0–945 px on the 7/6-bit fields; `height` is a 0–3 size preset (stock ZM never sets it and
its text renders, so 0 is a live value). One element = one row; the class hands out an index per instance
(`setup_clientfields`: `level.var_f70b6db[ hash( menu_name ) ]++`), so **N rows = N elements of the same
name**, no line cap, no fade unless asked. A highlighted row is a row with its own `red/green/blue`.

Every builtin involved is in the retail table (`reference/funcs_cw.csv`), none dev-flagged:

| side | builtin | address |
|---|---|---|
| server (GSC method on a player) | `openluielem( hash, idx [, flags] )` · `closeluielem( hash, idx )` | `+4d2c360` · `+4d591d0` |
| server | `registerclientfield( pool, name, ver, bits, type [, flag] )` · `codesetuimodelclientfield( player, name, value )` · `function_3ff577e6` (string/material field) | `+3b0a940` · `+3b69fd0` · `+3b0ac90` |
| client | `openluielem( lcn, hash, idx )` · `closeluielem` · `isluielemopen` | `+a403a30` · `+a4177b0` · `+a408b90` |
| client | `function_bcc2134a( lcn, hash, idx, field, value )` — set an element's data locally · `function_88759655` — read it | `+a40da60` · `+a412900` |
| client | `function_e231bfd4` / `function_9a992427` — register a luielem clientfield (the mirror of the server's) | `+36b5620` · `+375bea0` |
| both | `hash( str )` — the runtime name→hash stock uses for the element name | `+ca79170` |

**The system is live in MP.** Stock MP registers luielems on both sides: laststand's six `mp_revive_prompt`
(`mp_common/laststand.gsc:172` / `.csc:55`), `hud_spy` (`spy.gsc:136`), the infect/prop/scream timers,
`vip_notify_text`; `FullScreenBlack`/`InitialBlack` in every mode (`lui_shared.gsc:147-148`, `.csc:285-286`).
**`LUIelemText` itself is registered only by CP (`cp_common/util.gsc:181`) and ZM
(`zm_tungsten_side_quest.gsc:54` + `.csc:27`).** So an MP match has the machinery but no text element
registered on either side — and the dump ships no Lua, so whether the MP UI package even carries the
`LUIelemText` widget cannot be read off disk. That is the one question the probe asks.

## Two ways to drive it — and neither is free text

`lui_shared.csc` has two constructors for the same element, and they are not interchangeable:

| | server-driven (`register()`) | client-local (`register_clientside()`) |
|---|---|---|
| who opens it | server GSC: `player openluielem( hash, idx, flags )` (`lui_shared.gsc:50`) | the client script: `openluielem( lcn, hash, idx )` (`lui_shared.csc:49`) |
| how values travel | as **`clientuimodel` clientfields** named `luielement.<menu>.<idx><field>` — `clientfield_shared.gsc:37` `registerclientfield( "clientuimodel", … )`, `:192` `codesetuimodelclientfield` — mirrored on the client by `function_e231bfd4` (`clientfield_shared.csc:34`) | not at all — `set_data` → `function_bcc2134a( lcn, hash, idx, field, value )` (`lui_shared.csc:174`) writes the local element |
| needs on the client | the `.csc` mirror registering the same fields | the `.csc` doing the drawing |
| joiners | the server registers **new clientfields** a vanilla joiner's client does not have — the standing rule in `game-systems.md §2` says that can desync or crash them. Untested for this pool. Registering *last* (trailing indices the joiner is never sent, since the host never opens the element on a joiner) may make it inert — also untested | **nothing** — no registration, nothing replicated, nothing on a joiner's machine, by construction |
| free text | 💥 **no, measured on the client-local path (below) — and the field is the same type here.** The `text` field is registered through the bgcache-style registrar (`function_3ff577e6( "clientuimodel", "string", … )`), and **every stock writer of a luielem or clientuimodel "string" field passes a localized-string hash**: `zm_tungsten_side_quest_arcade_token.gsc:3177` `set_text( self, #"hash_1747569f8564a727" )`, `laststand.gsc:2496` → `revive_hud::set_text( …, #"hash_14cc93f11ba8334a" )`, the twenty `interactive_shot::set_text( player, #"hash_…" )` in `scene_player_shared.gsc:2081-2162`, `hudItems.cursorHintZMPurchaseInvalidText` ← `#"hash_6e3ae7967dc5d414"`, `hudItems.zmFeatureDescription` ← `#"hash_336cbe1bb6ff213"` / `#""`. Zero runtime-built strings in the dump. Same shape as `luinotifyevent`'s limit ([lui-events](lui-events.md)) | 💥 **no — measured 2026-09-13.** The value goes straight into the element model, and the widget's Lua **localizes it by key**: a key that is not in the client's string table is a **fatal `LUI Error … localizeentry`**, not a blank. Stock keys only, and a wrong key crashes the game |
| stock MP precedent | none for text | `lui::_screen_fade` uses exactly this form for `full_screen_black` (`lui_shared.csc:383-400`), and `callbacks_shared.csc:1397-1429` runs it in every mode |

▶ **So what the client-local form gives is positioned rows of STOCK strings** — any localized key the MP
client ships, each row with its own colour and alpha, no line cap, no joiner exposure — and the menu logic
would stay in `gunfight_menu.gsc`. It is a status panel, not a free-text menu. The free-text ceiling for a
panel is still the hint string ([hint-panel](hint-panel.md), region 4, unrun).

### The feed from GSC to CSC is not an unknown

The two VMs share dvars — not by assumption but by address: the CSC `getdvarstring` / `getdvarint` /
`getdvarfloat` **are the same builtins as the GSC ones** (`funcs_cw.csv`: pool `d7d4d00`, `exe+a2a4860` /
`+a2a4930` / `+a2a49d0` in both tables). That is the store the server menu's `setdvar` writes and the store
the in-process console `set` reached in the T1 bridge test. `gunfight_menu.gsc` writes rows into dvars,
the client polls them. The writes are the only new cost: the GSC-VM dvar store is finite (the 2026-09-13
crash dump read `Can't register more dvar` on the payload's 72nd pre-registered dvar), so **pack rows —
3–4 per string dvar with a separator the client `strtok`s** — and reuse the same names every paint; a dvar
costs a slot once per process, not per write. ⚠ Moot for text after the measurement below — a dvar can carry a
stock key name, but nothing that is not already a stock key may reach a text field.

## The probe — `src/gunfight_menu_c/` — RAN 2026-09-13

One `.csc`, one element, one question: **does the MP client's LUI draw a `LUIelemText` opened from an
injected client script, and does it draw a plain string?** It calls the two builtins directly (no class
syntax), on the pair that ran and printed in the match client VM on 2026-09-10:

```
hook     scripts\core_common\load_shared.csc
replace  scripts\core_common\radiation_debug.csc      (0 bytes; devgui.csc CRASHES here — frontend-link-set.md)
```

The first build opened element 0 of `hash( "LUIelemText" )`, wrote stock's post-open defaults
(`luielemtext.csc function_fa582112`) plus `x 40, y 48, alpha 1, white, left`, and set the text — ticks 1–2 the
stock key `#"mp/match_starting"`, tick 3 on the plain runtime string `"GF LUI <n>"`. Report line
**`77 L C O P nn`** (L literals intact · C `hash()` lowercases · O `isluielemopen` · P 1 stock key / 2 plain
string / 3 dvar · nn tick).

### What happened (klaze, `mp_village_rm`, `gunfight_menu` injected alongside)

| tick | feed | screen |
|---|---|---|
| 2 | `77111102` | ✅ **"Match starting"** drawn by the element — a widget the MP client had never opened for anything |
| 3 | — | 💥 **game crashed** on the plain-string set |

The crash dump (`crash_reports/BlackOpsColdWar.20260914-040712.zip` → `info.json`):

```

error_message  0x3580ada5,66e1ab67e305530b,localizeentry
lui_data       [C]: in function '4f9f1239cfd921fe'   x64:3786eefe1dee3f4a.lua:41
```

`66e1ab67e305530b` **is `hash64( "GF LUI 3" )` exactly** (`tools/crack-hash.py`; `mp/match_starting` hashes to
`73938fd7959ab087`, the key that rendered). So the widget's Lua takes the `text` model value, hashes it, and
calls the C localizer on it; a key that is not in the client's string table is a **fatal LUI error**, not a
blank and not a fallback to the raw string. `0x3580ada5` is not in `errors.tsv` (it is an LUI-error code,
`lui_code 100004`).

**Findings, both from one launch:**
1. ✅ `LUIelemText` is in the MP UI package. It opens from an injected client script with
   `openluielem( 0, hash( "LUIelemText" ), 0 )`, takes `function_bcc2134a` data, and renders a stock
   localized key. The literals survived the strip (`L=1`) and `hash()` lowercases (`C=1`).
2. 💥 **Free text on a luielem string field is closed by measurement.** `text` is localized-key-only, on the
   client-local path — the same type as all fourteen luielem `"string"` fields and the two `hudItems.*`
   string uimodels — and **an unknown key crashes the client**. No dvar-fed text, no runtime-built text,
   ever, on any of these fields. (The `gf_ui_probe` dvar phase was never reached; the dvar feed itself is
   still unmeasured, and is now moot for text.)

**Where it landed** (`C:/bocw/Screenshot 2026-09-13 210611.png`, the crash dialog already up, the element
still drawn): **middle-right** — the text's left edge at ≈75 % of the screen width, ≈61 % of the height, on a
16:10 display, with `x 40 / y 48` written. That is neither prediction: 15-px units from the top-left would be
(600, 720) → 31 % / 67 %; raw pixels would be the top-left corner. So the widget's anchor is something else
(centre-relative, not the corner — see the calibration run below). The rebuilt probe gave the two rows
different offsets; the run confirmed `x`/`y` work but with different per-axis scales.

### Calibration run — 2026-09-13 (klaze, `mp_farm`, `Screenshot 2026-09-13 212156.png`)

Feed **`77111105`** = L1 C1 **O1** P1, tick 5. Both rows drew, no crash. Four things measured at once:

- ✅ **Two `LUIelemText` of the same name coexist** (`O=1` needs both open) — N rows = N indices, confirmed.
- ✅ **Per-row colour works** — row 0 white "Match starting", row 1 yellow "Waiting for more players...".
- ✅ **`x` and `y` are both honoured and independent** — row 1 (`+10 x, +4 y`) drew right of *and* below row 0,
  not stacked. So the client-local `function_bcc2134a` path positions elements; no clientfield needed.
- **Anchor + scale (rough, from two points on one screenshot, ~2000×1245):** row 0 `(40,48)` → ≈`(1480,747)`,
  row 1 `(50,52)` → ≈`(1540,822)`. That gives **y ≈ 15–20 px/unit** (4 units → ~75 px — consistent with the
  server `/15` convention *and* with the 6-bit `y` range mapping to screen height: 63 → 1245 ≈ 19.8 px/unit),
  and **x much finer, ≈6 px/unit** (10 units → only ~60 px). ⚠ The `x` figure is the shaky one — the on-screen
  horizontal gap is small and eyeballed. The two axes are **not** the same scale, and the origin is not the
  corner: solving `screen = off + scale·model` puts `x=0` near 62 % width and `y=0` above the top edge.
- ✅ **Stable for a full round** — the feed line ticked up every 5 s for the whole round (klaze), so the `.csc`
  `while` loop and the open elements survive the round with no crash and no hang. The 2026-09-13 crash was the
  plain-string localize specifically, not the element or the loop.
- ⚠ So placement is real but the coordinate space is not pixels and not the `/15` model on both axes. **A clean
  layout needs one more probe** with wide, unambiguous offsets — e.g. row A `(0,0)`, row B `(100,0)`, row C
  `(0,60)` — read three corners off one screenshot and the mapping falls out exactly. Only worth it if the
  stock-string panel is actually wanted.

## Stage 2 — boxes / bars (`LUIelemImage`, BUILT 2026-09-14, unrun)

The one part of the luielem system the localize wall does NOT cripple: `LUIelemImage` is a positioned
rectangle (`x` 7 · `y` 6 · `width` 6 · `height` 6 · `alpha`/`red`/`green`/`blue` 4-float · `material`). It
takes a **material**, not a localized string — so a coloured box/bar has no key to get wrong. The catch: the
`material` field is an asset lookup, **no stock script ever sets one**, and by the text-crash precedent a bad
material name may be fatal.

`src/gunfight_menu_c/` now draws two boxes alongside the two proven text rows (one payload — the client pair
has one replace target, so text and image share it). Report line is **`78 T I M nn`** (T both text rows open ·
I both boxes open · M material-phase · nn tick).

- **The safe question first — does rgba alone fill a box?** The image reset sets `material` to `#""`, so
  opening one is safe; the boxes are drawn from colour + size with material left `#""`. If a red bar
  (`x20 y20 w30 h8`) and a semi-transparent green square (`x25 y30 w15 h15`) appear at `M=0`, **boxes/bars
  work with zero material risk** — that is the win, and it is done.
- **Material is opt-in and gated behind a dvar.** Only if `gf_img_mat` is non-empty does the payload set a
  material (hashed), on both boxes. Enable it **only if the rgba boxes are invisible**, on a launch you can
  lose: `python tools/gf-bridge/bridge_channel.py "set gf_img_mat white"` (then `black`). Candidates are
  `"white"`/`"black"` (39 dump uses each). A crash with `error_message` hash == `hash("white")`
  (`4ed973885856e206`) means material lookup is fatal on a name the client lacks as an asset — try the other,
  then stop. The crashing-text build stays `payloads/gunfight_menu_c.crashed-plainstring.cscc`; the 2-text-row
  build is `payloads/gunfight_menu_c.text-2rows.cscc`.

### Boxes RAN 2026-09-14 — the element opens but will not fill (blocked on material bgcache)

| build | feed | screen |
|---|---|---|
| rgba only, material `#""` | `78110005` (T1 **I1** M0) | text rows drew, **no box** — rgba alone does not fill |
| material `#"white"` on both | `78111nn` (T1 I1 **M1**) | **no box, no crash** — `white` null-resolved |

So `LUIelemImage` **opens in MP** (`I=1`, two instances coexist) but draws nothing without a material, and a
material name no-ops instead of filling. Diagnosis:

- The `material` field is registered with **`function_dcb34c80` — the same bgcache registrar as the text
  field** (`luielemimage` `function_dcb34c80( "material", "material", 1 )` vs `luielemtext`'s
  `( "string", "text", 1 )`). So a **hash is the right form** (text proved it) and `#"white"` is a real fill
  material (stock `setshader( #"white", w, h )`, 31 sites). The value and form are correct.
- Text resolved because the **localization table is globally present**; a **material must be precached into
  the client element's bgcache**, and the bare-`openluielem` path (the one that works for text) **never sets
  up a material bgcache**. **No stock script anywhere sets a `LUIelemImage` material** (0 `set_material`
  callers), so nothing precaches one for us to ride on — the field appears to be unexercised in shipped content.
- Not a crash (unlike a bad text key): a missing material resolves to null and draws nothing.

**SWING 2026-09-14 — every value FORM tested, none fill.** A 10-box column set material to int indices 0..7
(bgcache-index hypothesis) and raw strings `"white"`/`"$white"` (name hypothesis): feed `78110004` = all 10
open, **zero bars drew**. With the earlier `hash("white")` that is hash, int-index and raw-string all null,
no crash. So no value form resolves from the bare-open path — confirming the material needs a bgcache the
element never got.

⇒ **Boxes/bars are blocked** on material precaching the injected client-local path can't do. Reaching it would
mean driving the element's full `register_clientside` + a material bgcache the client script populates — deep,
speculative (bgcache from an injected `.csc` is untried), and low ROI for "would be nice". **Recorded as
blocked, not impossible.** The builds are kept: `payloads/gunfight_menu_c.text-2rows.cscc` (the clean text
result), and the current file is the white-material image build.

## What is left of the route

- **A positioned status panel of stock strings**: map name, gametype name, "Match starting", team words,
  outcome words — every key the MP client ships, one element per row, coloured, anywhere on screen. Useful
  for a caster/host overlay; useless for menu rows that name a setting and a value.
- ⚠ **Every key must be proven to exist before it ships** — the only test is "did it crash", and a miss is
  fatal. Take keys only from stock MP call sites (`grep -rhoE '#"mp/[a-z0-9_]+"' scripts/mp_common`, ~30 named
  ones, plus `game.strings` in `globallogic.gsc`). `makelocalizedstring` is a dev builtin (type 1 — the class
  that crashed as `openfile`); `getlocalizedstringindex` (server, `+a03df60`) is untested as a validator.
- **Numbers**: no numeric field on the text element, and digits are not localized keys. A countdown stays
  `luinotifyevent( #"create_prematch_timer" )` ([lui-events](lui-events.md)); a count stays the feed.
- The `gf_menu_region 5` free-TEXT layout is **withdrawn** (crash wall); the hint panel (region 4) is the
  free-text panel. But `LUIelemImage` boxes/bars (Stage 2) are a live graphics layer — a background panel or
  highlight bar *behind* the hint-panel menu, or a visual timer/capture bar — that neither feed nor hint can draw.

## Untried — not ruled out

- `player openluimenu( "MPHintText" )` + `setluimenudata( h, #"hint_text_line", str )` (`mp_common/util.gsc:933`)
  and `lui::timer`'s `openluimenu( "HudElementTimer" )` with `x`/`y`/`height` (`lui_shared.gsc:365`) are
  server-side, need **no** client payload and **no** clientfield, and `setluimenudata` takes plain strings in
  dev code (`face.gsc:253`, `"MISSING VO SOUND"`). ⚠ After today, assume a LUI menu's Lua localizes a string
  it is handed the same way — a plain string may be the same fatal error. Probe it with a stock key first,
  and only then a plain string, on a launch you are prepared to lose. No MP stock caller of `show_hint_text`,
  so the widget may not ship in the MP package at all.
- **Which keys exist**: build the list of MP localized keys that stock passes (`#"mp/…"`, `#"mpui/…"`,
  `game.strings`) and prove each once; a proven list is what makes a stock-string panel shippable.
- **The server-driven form with the registrations placed LAST** (after every stock `registerclientfield`, at the
  end of `__init__`): if trailing `clientuimodel` indices the host never sets on a joiner are simply never sent,
  the joiner-desync objection may be moot and stock-key rows could be pushed from the server with no client
  payload at all. Hash-only text either way (measured). Test with one joiner, never with the vanilla-friends
  rule in force.
- **`LUIelemImage` with a plain material name** (`"white"`, `"black"`) on the client-local path — a box and a
  highlight bar. No stock caller sets a material, so the value shape is a guess.
- **`closeluielem` + reopen across a round boundary** — whether the element survives the HUD rebuild or the
  client script must reopen it (the probe reopens on the next tick after a close, so a blank of up to 5 s at
  the round change is the tell; `O` reads 1 again once reopened).
